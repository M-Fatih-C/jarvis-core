# JARVIS V1 operation

The Mac is the execution authority. The iPhone authenticates with Firebase and creates immutable `queued` commands. Firestore rules bind their owner and prohibit client results, leases, or approval-state changes. The Mac verifies the owner, policy, action digest, expiry and one-time approval before any write.

## Local configuration

Keep `.env`, `GoogleService-Info.plist`, databases, encryption keys and provisioning files out of Git. Download the iOS Firebase configuration to `ios/JarvisiOS/JarvisiOS/GoogleService-Info.plist`; Build Manager embeds it through an explicit Xcode script input. CI uses the empty example configuration and cannot authenticate.

Set `FIREBASE_PROJECT_ID`, `JARVIS_UID` (the actual Firebase Authentication UID), and `FIREBASE_ENABLED=true` only after creating the owner's account. Deploy `cloud/firestore.rules` to that project. Production requires native macOS tools and local semantic embeddings; mock tools or a configured emulator are rejected.

Build the existing MacAgent application, then run:

```sh
.venv/bin/python scripts/install_launch_agents.py --install
```

The user LaunchAgents start MacAgent and the loopback Core API after login and restart failed processes. Logs are under `~/Library/Logs/Jarvis`. A loaded model is necessary but does not prove iPhone acceptance. Device health comes from authenticated Firestore heartbeats and becomes stale after 100 seconds.

## Consent and private memory

Existing encrypted imports do not grant consent. PRIVATE reads require a trusted authenticated identity, the interactive-query purpose, permitted categories and a matching, explicitly granted category consent. General cloud chat and email analysis do not receive private authorization contexts.

Inspect or change consent locally with `scripts/manage_consent.py status`, `review`, `grant --category ...`, or `revoke --category ...`. Grants bind to the configured `JARVIS_UID`. Revocation preserves ciphertext and keys. Source dates and verification states remain part of memory context. Historical sample class schedules are not confirmed current events.

New records bind AES-GCM authentication to the record ID and schema version. Unmarked old ciphertext is not silently retried without AAD; only explicitly marked schema-zero legacy envelopes qualify. Do not relabel or delete old data to bypass verification.

## Recovery semantics

- Firestore transactions reserve command IDs and idempotency keys. Expired leases can be recovered before execution; an interrupted RUNNING command fails with an uncertain-outcome message and is never automatically replayed.
- A result-write interruption retries the same result. iPhone foreground/relaunch resumes reads using persisted owner-scoped IDs, never resubmitting an uncertain mutation.
- ApprovalStore and active model context are in memory. Restarting Core invalidates pending approvals; request a new proposal. Conversation identifiers survive iOS restart, but Mac conversation history is not persisted across Core restart.
- If a multi-action request reaches its execution limit after confirmed writes, its failure reports the number of completed actions. Review existing results before issuing another request; it does not roll back or repeat completed writes.
- Gmail persists history cursors only after successful reads, paginates initial/history recovery, and retries stored but unprocessed messages. It does not send email. Important notifications contain generic text, never subjects or memory payloads. A reserved notification with an uncertain delivery is not replayed; this favors avoiding duplicate alerts over guaranteed delivery.

## Optional schedules

Both schedules require explicit opt-in. Gmail uses `EMAIL_SYNC_SCHEDULE_ENABLED=true` and `EMAIL_SYNC_TIMES='["09:00","20:00"]'`, with `DEFAULT_TIMEZONE=Europe/Istanbul`. A persisted successful-run watermark and lease prevent repeated successful batches and coalesce missed slots after sleep into one catch-up run. Initial activation processes eligible pending local intake. For new-mail-only monitoring, `EmailStorage.set_monitoring_start()` persists an explicit UTC boundary: earlier stored messages remain intact but cannot enter background analysis, and old messages returned by initial/history recovery are skipped. Keep this boundary across restarts; do not reset it at each scheduled check.

Build Manager's persisted `auto_renew_enabled` setting controls renewal. After opting in, rerun the LaunchAgent installer to install its 15-minute evaluation job. It attempts renewal when the embedded profile has at most two days left, on the previously approved device, with bounded retries and cooldown. A newer valid profile AND a verified installation are required to record successful renewal. Compilation alone reports a generated profile requiring installation. Locked devices or Apple sign-in requirements report `USER_ACTION_REQUIRED`; no signing restrictions are bypassed.

Routine device-unavailable probes and build/install successes are silent. Actionable signing or installation failures use generic Turkish banners without sound, with one alert per failure type per 24 hours persisted across daemon restarts. Diagnostic details stay out of notifications.

## Physical acceptance

Use the installed iPhone application, not a script impersonating it:

1. Create/sign in to the owner's Firebase account; configure that UID on the Mac.
2. Send a message and receive real local Qwen output through production Firestore.
3. Ask about universities and the current week. Check source dates, historical schedule warnings and actual EventKit query results.
4. Request a synthetic event; inspect its title, times and other actual arguments in the approval card, approve once, and verify native EventKit read-back and the final phone result.
5. Tap the microphone to open voice chat and start capture; tap “Bitir ve gönder” to submit. Verify audible Turkish output, input RMS animation, output audio metering, manual interruption and foreground-only capture. Conversation mode is optional.
6. Restart the Mac, log in and repeat a read-only phone query. Process restart tests alone do not prove a full reboot or sleep/wake cycle.
7. Unplug USB and update through Build Manager. Verify CoreDevice `localNetwork`, bundle/build version, provisioning validity and a non-sensitive app-container sentinel before/after installation.

Do not call a successful simulator, mock, emulator or Mac-only request a physical iPhone acceptance result.

## Calendar and CarPlay briefing

The phone calendar screen reads native EventKit through authenticated, owner-scoped, read-only Firestore commands. It defaults to all calendars and distinguishes a failed read from a genuinely empty day. Dates use Europe/Istanbul. Calendar reads do not enter pending chat mutation recovery.

Build 16 exposes an App Intent, `Yolculuk özetini al`, for a Shortcuts CarPlay connection automation. It produces a deterministic Turkish greeting, date, up to three remaining calendar entries, and fresh Mac/model/worker health. It never creates events or submits approval decisions. Weather is an explicit string input supplied by Apple Shortcuts, not invented by the model. No agenda cache is treated as current. A stale heartbeat or read timeout produces an unavailable message. The intent can run while locked after first unlock, using the existing Keychain session; configuring the personal automation is an explicit user action on iPhone.

See [Turkish setup instructions](../CARPLAY_SETUP.md). This is an audio greeting automation, not an entitled CarPlay dashboard app. Physical vehicle connection, audio routing, and locked-screen execution require a real car test; an Xcode build is not that test.
